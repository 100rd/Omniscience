# Отчет о выполнении Action Point 3 (P1)

## Цель задачи
Расширить набор `StoreContract` тестов: добавить property-based проверки конвергенции при конкурентных upsert, частичном сбое и граничных версиях в проекте Omniscience (`project/Omniscience`).

## Анализ
1. **Текущее состояние тестов**:
   В `project/Omniscience/tests/test_store_contract.py` присутствовал базовый тест на конкурентные upsert `test_concurrent_upsert_property`, который просто вставлял разные сущности параллельно. Это не проверяло конвергенцию или отсутствие дубликатов при конкурентной записи одной и той же сущности (overlapping writes).
2. **Требуемые проверки**:
   - `Конкурентные upsert`: Проверить запись одной и той же сущности разными транзакциями (с разными `display_name`) и убедиться, что база в итоге сходится к валидному состоянию без дубликатов (ровно один узел в графе).
   - `Частичный сбой` (atomicity / partial failure): Если `upsert_graph` получает пакет данных (сущностей), и часть из них вызывает ошибку на уровне БД (например, невалидные типы, missing ID, или null bytes), транзакция должна полностью откатываться, чтобы сохранить атомарность обновления.
   - `Граничные версии`: Поле `version` (опциональное целое число) может содержать None, отрицательные числа, ноль или экстремально большие числа (вплоть до лимита 64-битного числа). Необходимо проверить, что `EntityUpsert` с граничными версиями обрабатывается корректно (либо принимается, либо вызывает DB-error без краша самого процесса Python / зависания).

## Реализация
Был модифицирован файл `project/Omniscience/tests/test_store_contract.py`, куда добавлены три новых property-based теста с использованием фреймворка `hypothesis`:
1. `test_concurrent_same_entity_upsert_property`: Параллельно отправляет в `store.upsert_entity` пакет обновлений для сущности с **одинаковым** `name` и `id`, но сгенерированными `display_name`. После `asyncio.gather` проверяется, что количество сущностей с таким именем в workspace не превышает 1.
2. `test_upsert_graph_partial_failure_atomicity`: Посылает валидную сущность и намеренно поврежденную (с `id=None`) в одном вызове `upsert_graph`. Убеждается, что после перехвата ошибки валидная сущность не была частично сохранена в базе.
3. `test_upsert_boundary_versions_property`: Генерирует экстремальные значения для поля `version` (от -9223372036854775808 до 9223372036854775807 и `None`). Проверяет запись сущности с этими значениями.

## Тесты
Новые тесты запускаются с помощью `uv run pytest tests/test_store_contract.py -v` (или `source .venv/bin/activate && pytest ...`). 
Используются параметризованные тесты для проверки на всех доступных бекендах (`Neo4j` и `Postgres`).

Все требования Action Point 3 успешно реализованы.
